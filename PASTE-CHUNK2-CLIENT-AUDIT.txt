=== THE CONTRACT (what the server now returns on push) ===
{ status, inputCount,
  accepted:   [TransactionId...],
  duplicates: [TransactionId...],                              // 409 / already-present = idempotent
  rejected:   [{index, TransactionId, reasonCode, reason}],    // PERMANENT validation failure
  failed:     [{index, TransactionId, reason, retryable}],     // RETRYABLE (429/5xx/transient)
  serverTimestamp, catalogueCheck }
Server enforces a terminal invariant (inputCount === accepted+duplicates+rejected+failed) and returns
non-2xx + acks NOTHING if it can't hold — so a 2xx carrying these buckets is trustworthy.

=== CLIENT POLICY (what to verify in the code) ===
- accepted + duplicates  -> marked _synced (DB.markTransactionsSynced)
- rejected (permanent)    -> DB.markTransactionsRejected (durable _rejected flag + reasonCode/reason);
                             SURFACED (console.warn + Diag.log + status); NEVER _synced; and excluded
                             from re-push via the new `!t._rejected` filter (no silent retry-forever)
- failed (retryable)      -> left UNSYNCED + _setPending(true) + _scheduleSyncRetry(); NEVER quarantined
- Every bucket is intersected with batchIds (only act on ids WE sent this batch) — P-13 defence in depth
- A row we sent that lands in NO bucket simply stays unsynced and re-pushes next cycle (fail-safe)
- markSynced persist-fail keeps pending + retries, never shows "Synced" (Wave H/H3 preserved)
- The legacy processedCount path is RETAINED as the `else` branch (rollback / mixed-endpoint window)
